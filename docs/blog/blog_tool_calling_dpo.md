# 我给一个小模型做工具调用偏好对齐，顺便把整条流水线的 6 个 bug 都挖了出来

> 项目：Qwen2.5-1.5B 工具调用智能体的 DPO 偏好对齐优化
> 硬件：单卡 3090 24G
> 代码：见仓库根目录 `README.md`

---

## 0. 先说结论

我做的事，一句话：**让一个 1.5B 的小模型在被用户指出错误之后，真的会改。**

听起来是个很小的目标。但它背后是三件独立的难事——把意图落成合法的工具调用、记住工具名白名单不能自己造、被纠正后放弃上一轮的输出重新推理。

更重要的是：我把这三件事**拆成了可以分别度量的指标**，然后为每一类错误设计了一类偏好数据。

这篇文章主要讲两件事：

1. **方法**：为什么我把「准确率」换成了 `pass^k`，为什么偏好数据要分四类而不是一类。
2. **工程**：我在没有 GPU 的情况下写了一条 mock 流水线，它抓出了 6 个真实 bug——其中 3 个如果留到 GPU 上才发现，会各自烧掉几个小时。

---

## 1. 为什么不用准确率

一开始我想得很简单：跑 100 个任务，数对了多少，就是准确率。

跑起来就发现不对。

小模型的行为不是「稳定的对」或「稳定的错」，而是**飘**。同一个任务，采样 4 次，可能对 2 次错 2 次。用单次准确率衡量，它和「4 次全对 2 次、4 次全错 2 次」的模型看起来一模一样——都是 50%。

但这两个模型的可用性完全不同。前者你不敢上线，后者你至少知道哪些任务不能给它。

所以我换成了 **pass^k**：一个任务采样 k 次，**k 次全部正确**的概率。

它和 pass@k（k 次里**至少一次**正确）是一对：

- `pass@k` 高说明「能力上限够」
- `pass^k` 高说明「能力稳定」
- 两者之差 `Δstability = pass^k − pass@k` 就是「会做但不稳」的程度

`Δstability` 越接近 0 越好。这是我认为比准确率有意义得多的一个数。

**这里有个实现细节值得说**：pass^k 不能直接算成 `(c/n)^k`。那是把「从同一批样本里取 k 个」当成了「独立重采 k 次」，在 n 小的时候偏差很大。

正确的无偏估计是组合数形式：

```
pass@k = 1 − C(n−c, k) / C(n, k)      至少一次成功
pass^k =     C(c,   k) / C(n, k)      k 次全部成功
```

n=4, c=2, k=2 时，朴素估计给 0.25，无偏估计给 1/6 ≈ 0.167。差了 50%。

而 τ-bench 报告 pass^4 时 n 通常就等于 4，此时无偏估计退化成 0/1（要么 4 次全对要么不是），所以我在报告里同时给一个有偏的 `(c/n)^k` 作为参考值，并标注它是有偏的。主指标仍然用无偏的。

## 2. 为什么偏好数据要分四类

DPO 的基本设定是：给模型看成对的样本，告诉它「这个比那个好」。

朴素做法是随便找点偏好数据训一下。但那样你根本不知道是哪一类数据在起作用——甚至不知道有没有起作用。

所以我先把基线模型的错误**分类**：

| 错误类别 | 具体表现 |
|---|---|
| 格式错误 | 不输出 `<tool_call>`，只回一句「我来帮您查询」 |
| 工具幻觉 | 调 `find_flights` 这种不存在的工具 |
| 工具选错 | 工具名合法但不是该用的那个 |
| 参数错误 | 工具对了，参数填了 `previous_booking` 这种占位符 |

然后为每一类设计**一种偏好对的构造方式**，形成一对一映射：

| 偏好对类型 | 针对 | chosen ↔ rejected |
|---|---|---|
| 格式约束对 | 格式错误 | 合法 JSON ↔ 纯文本承诺 / 坏 JSON |
| 工具选择对 | 幻觉 / 选错 | 白名单工具 ↔ 命名变体假工具 |
| 参数约束对 | 参数错误 | 真实实体 ↔ 占位符 / 错一个字符 |
| **错误恢复对** | 被纠正后不改 | **纠错后修正** ↔ 原样重复 |

这样消融实验就干净了：训「只有格式对」的数据，看格式率涨不涨、其他指标动不动。

### 错误恢复对是这套里唯一真正原创的东西

其他三类偏好对，本质上是「把正确答案和错误答案摆在一起」，SFT 用 chosen 也能学到不少。

但**错误恢复**不一样。SFT 的 chosen 里永远只有正确答案，模型学不到「先错后改」这个模式——因为数据里根本没有这个模式。

所以我构造的 prompt 长这样：

```
system:  你是航空客服助手，可用工具...（工具清单 + 格式规范）
user:    把订单 BK7F2A9C 的行李额度改成 30 公斤
assistant: <tool_call>{"name": "check_baggage", ...}</tool_call>    ← 模型的首轮错误
user:    我不是要查询，我是要改成 30 公斤，请用修改额度的工具。
assistant:  ← 在这里比
```

`chosen` 是改对之后的正确调用，`rejected` 是原样重复上一轮的错误。

这个 prompt 的构造是关键：**它把「用户纠错」这个事件本身放进了上下文**。普通 instruction tuning 数据里拿不到这个信号。

## 3. mock 流水线：没有 GPU 的时候该做什么

我没有 GPU。租之前我想先把代码写完，但不能写完就赌它是对的——那等于把调试成本转嫁到 GPU 机时上。

所以我写了一条 **mock 流水线**：把策略换成合成的，其余一切都是真的。

```
评测 → 解析 → 错误分类 → 偏好数据构造 → 质量门禁 → DPO 训练 → 再评测 → 出图
  ↑合成       ↑真      ↑真        ↑真         ↑真      ↑真       ↑真      ↑真
```

这个设计的关键在于：**只有「策略」是假的**。所以链路上任何一处逻辑错误都会被真实执行并暴露出来。

结果它帮我抓了 6 个 bug。

### Bug 1：错误类型键的大小写不一致

我在配置里写的是 `"format_error"`，代码里查的是 `FORMAT_ERROR`。

`dict.get()` 遇到不存在的键返回默认值，不报错。所以所有错误都被静默归成了「格式错误」——错误分布图看起来正常，但整个是错的。

**教训**：字符串键做跨模块标识时，应该用常量而不是字面量。我把所有键统一成 `error_taxonomy` 里的类别常量了。

### Bug 2：成功概率与错误率脱钩

这个最隐蔽。

我最初的设计是：给每个实验设一个「成功率」和一个「各类错误的相对权重」。看起来合理。

然后我发现：把格式错误率降低 65%，指标**纹丝不动**。

原因是我把成功概率独立设定了。降低格式错误只是把概率质量从「格式错误」挪到「其他错误」，成功率不变。

正确的结构是让成功成为**补集**：

```
p_success = 1 − Σ p_err(e)
```

这样改善一类错误释放出来的概率质量才会真正流向成功。改完之后四个实验才产生了可区分的差异。

**教训**：建模的时候要检查「改动是否真的能传导到目标量」。如果两条路径独立，你的实验设计就是空的。

### Bug 3：偏好对去重键过粗

我用 `(prompt, chosen)` 做去重键。结果 97% 的候选数据被判为重复丢掉。

原因：同一个任务 + 同一个正确回复，可以配很多不同种类的负样本（坏 JSON、纯文本、错工具名、错参数）。这些在 `rejected` 上完全不同，是**独立有价值**的训练信号，却被我的去重键当成同一条。

改成 `(pair_type, prompt, chosen, rejected)` 之后，可用数据量涨了 30 倍。

### Bug 4：纠错话术与错误类型不匹配（危害最大）

我从一个纠错话术池里随机抽句子。

于是生成了这样的训练数据：

```
user:      2025-07-25 从上海去广州有哪些航班
assistant: <tool_call>{"name": "search_flights", "arguments": {"origin": "上海", ...}}</tool_call>
user:      city 参数要填中文城市名，不要填三字码。        ← 这句话和场景无关！
assistant: <tool_call>{"name": "search_flights", "arguments": {"origin": "SHA", ...}}</tool_call>
```

用户的纠错话术在说 `city` 参数，但这一轮根本没有 `city` 参数——这是航班搜索，用的是 `origin`/`destination`。

而且更要命的是：模型输出的**修正是对的**（改成了三字码），但用户的话术在指一个不存在的问题。

**这种数据比没有数据更糟**：它在教模型「用户的纠正可以忽略」。

我加了一个门禁 `_recovery_coherence`：纠错话术里提到的参数名，必须真的出现在首轮错误调用的参数里。同时把话术池按错误类型拆开（机场三字码类、城市名类、日期类、占位符类……），让每个场景只从匹配的那一组里抽。

这个门禁上线后又拦下了 355 条不连贯的样本。

**教训**：合成数据最危险的不是「不够好」，而是「自相矛盾」。前者只是没帮助，后者会教坏模型。所以合成数据必须有**语义连贯性**的自动检查，不能只检查格式。

### Bug 5：变量名遮蔽

```python
candidates = [t for t in tasks if t.expected.tool]   # 外层
while ...:
    ...
    else:
        candidates = [f for f in fakes if f != tool]  # 内层覆盖了外层
        fake = rng.choice(candidates)
    ...
    task = candidates[i % len(candidates)]            # 现在 candidates 是字符串列表
```

直接崩。低级错误，但如果没有 mock 流水线，它会在 GPU 上第一次跑训练时才崩——而你已经在等数据加载了。

### Bug 6：`log_sigmoid` 的符号精度问题

这个是测试发现的，不是流水线发现的。

```
log σ(x) = −log(1 + e^{−x})
```

在 x < 0 时，`e^{−x}` 会很大，所以要变形。我第一次写成：

```python
return -math.log1p(math.exp(x))    # 错
```

x ≈ 0 时看不出问题。但 `log σ(−20)` 应该是 −20，这个式子给出 −2e−9。

正确的变形是：

```python
return x - math.log1p(math.exp(x))
```

我写了个测试覆盖远离 0 的取值才发现。**教训**：数值稳定性的测试必须覆盖极端取值，x≈0 附近的测试对这类 bug 完全无感。

## 4. mock 的误差率是「假设」不是「结论」

这里必须说清楚，否则整篇文章的可信度都完了。

Mock 流水线里那些「基线 51.5%、联合方案 78.8%」的数字，是**我喂进去的假设**。它们唯一的作用是验证「假设 → 指标」这条映射链在工作。

所以我在工程上做了三重隔离，确保这些数字不可能被误当成结论：

1. 文件名带 `.mock` 后缀（`eval_report.mock.json`）
2. 文件内容带 `"is_mock": true`
3. 汇总脚本**默认拒绝读取** mock 报告，必须显式加 `--include-mock`，而且输出文件名和表格标题都会标注 SIMULATED

第 3 条是最重要的。如果只是「在文档里写一句这是模拟数据」，早晚会有人把数字粘错地方。

## 6. 几个我觉得值得记下来的取舍

**评测口径选了「目标轮」而不是「完整多轮」。**

给定确定的多轮前缀，评模型的这一轮输出。好处是 ground truth 完全确定、`pass^k` 可比。代价是忽略了多轮累积误差。完整的自动多轮评测需要真实的用户模拟器（对标项目用了 72B），超出单卡预算。所以我另写了一个 `eval_recovery.py` 走真实多轮，专门测恢复率，作为补充。

**偏好数据的 `chosen` 是构造的，不是大模型生成的。**

原始规划里写的是用 72B 生成 chosen。实际实现改成直接从任务 ground truth 构造。好处是完全可控、可复现、零 API 成本；代价是 chosen 的自然度不如大模型生成，可能和真实分布有偏差。我认为在这个规模的项目上，可复现性更重要。

**主动设计了可能推翻自己论点的对照组。**

`dpo_recovery` 这个实验的卖点是「对比信号是必要的」。但「必要」这件事需要一个反例来支撑：如果直接用 chosen 做 SFT 就能达到同样效果，那提升就来自「更多监督数据」而不是「对比学习」。

所以我加了 `sft_only` 对照组，而且它的数据**有意不含错误恢复对**——因为恢复能力无法由「只有正确答案」的数据教出来。如果 SFT 组在恢复率上也涨了，那说明整套论证有问题，结论需相应改写。

这条我认为比任何指标都重要：**实验设计里必须留一条能推翻自己的路径**。
