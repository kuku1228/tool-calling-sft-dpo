## Q1 「你这个项目做了什么？」

**一句话**：在航空客服领域构建了一套**工具调用 agent 的偏好优化流水线**，
把 1.5B 模型在 100 任务基准上的准确率从 **50.25% 提到 83.00%**，
并搭了一套多轮 agent 执行循环来评测「不给现成答案时模型能否自己取信息」。

**三层结构**（先说清，避免对方以为只是一次 SFT）：

| 层 | 内容 | 关键产出 |
|---|---|---|
| 数据层 | 7 类错误分类体系 + 5 类偏好对构造器 | 139 个合成训练任务、5 类偏好对 |
| 训练层 | SFT 对照 + DPO（从基座 / 从 SFT 续训） | 6 组真实实验 |
| 评测层 | 单轮基准 + **多轮 agent 循环**（含故障注入） | 8 组指标 |

**主动提一句**（这会引出最有价值的部分）：

> 过程中我发现自己的主结果有**数据污染**，主动推翻重做了。
> 如果只报 95% 那个数字，它经不起追问。

## Q2 「为什么 DPO 没有赢过 SFT？」★高频

**一句话**：三个原因叠加 —— **统计功效不够、超参不适合 LoRA、任务本身不需要对比信号**（最后一条部分不成立，见 Q5）。

### 原因 1：统计功效不够（这是最硬的答案）

> ### ⚠️ 本段判据已被修正（2026-10）
>
> 旧版写的是「实测 CI 宽度 ≈ ±10pp」。**两个问题**：
>
> 1. 那个 ±10pp 是**从一次测量推断的**，不是可以直接引用的实测值
> 2. 更根本的是：我原先用「两个 CI 是否重叠」判断显著性 ——
>    **那是错的**。配对数据必须用配对检验（McNemar / 配对 bootstrap），
>    「CI 重叠」不构成「无差异」的证据
>
> **现在能给的只有公式化的 MDE**（最小可检测效应，配对设计、任务级）：

```
MDE = (z_{1-α/2} + z_power) * σ / sqrt(n)
    = (1.96 + 0.84) * σ / sqrt(n)

任务级二值结果在 p≈0.5 附近时 σ ≈ 0.5：
    100 任务 → MDE ≈ 0.14
    400 任务 → MDE ≈ 0.07
```

**所以「差 3 个百分点」这类结论在 100 任务规模上不可能获得统计支持。**

**而且「扩到 400 个任务」这个方案我最后否决了** ——
因为它只带来「表面文本唯一」，真正不同的骨架只有 208 种，
有效独立样本不是 400。**那个更窄的 CI 是虚假精度。**
正确做法是**100 个真正独立的任务**（v3：骨架/任务比 0.99）。

### 原因 2：对比信号会损害任务执行能力（**我做了关键实验去验证，结论是 β 不是主因**）

我原本以为崩塌源于 **β=0.1 不适合 LoRA**，于是做了修正实验
（β=0.5、lr=1e-5、1 epoch，从干净的 sft_v3 83% 起点出发）：

| 实验 | 起点 | accuracy | 格式正确率 |
|---|---|---|---|
| `dpo_from_sft` | sft_only | **10.0%** | 0.0% |
| **`dpo_sft_v3_b05`** | **sft_v3 83%** | **49.25%** | 58.8% |

**β 提高 5 倍，仍然崩塌 33.75pp。所以「β 是崩因」这个归因是错的。**

**真实失效机制**：失败子类型显示 **`clarify_instead` 54 条**（sft_v3 只有 20），
`booking_flow` 从 72.2% 掉到 **16.7%**、`multi_tool` 从 100% 掉到 **33.3%**。

> **DPO 学会了一个全局的行为倾向（「遇到不确定就追问」），
> 而不是有条件的判断规则（「信息不足时追问，信息充足时执行」）。**
>
> **偏好对只告诉模型「A 比 B 好」，没有告诉它「A 在什么条件下比 B 好」。**

### 原因 2 的原始分析：β=0.1 的训练轨迹（保留）


`dpo_from_sft` 崩塌的训练轨迹：

```
              step 5      step 25     step 55     step 120
logps/chosen  -6.00  →   -13.74  →   -28.42  →   -25.09    ← 对正确输出越来越没把握
logps/rejected -35.2 →   —       →   —       →  -177.07    ← rejected 崩得更狠
rewards/margins +0.34 →  +7.80  →   +10.29  →   +12.19    ← 过优化 6 倍（常见目标 ≈2）
训练 loss      4.52  →   —       →   —       →     0.0208  ← 看起来完美
评测 format_accuracy                           →     0.0%   ← 实际完全崩了
```

**关键点**：训练 `loss` 降到 0.02、`rewards/accuracies` 达到 1.0 —— **两个指标都在说「训练成功」**，但 `logps/chosen` 的**绝对值**在恶化。

> **`β = 0.1` 来自 DPO 论文，但那是全参微调的设置。**
> LoRA 参数量少得多，同样的 β 意味着「用更少的参数做更大的分布偏移」→ 更易过优化。

**可能的追问**：「你怎么知道是 β 的问题而不是别的原因？」
**答**：因为有对照 —— 同一份数据、同一个起点，只有 β 不同（另一组是 0.1 但只跑 1 epoch 就崩）。
另外**训练指标健康但评测崩了**，这排除了「训练没跑起来」，指向过优化。

### 原因 3：从基座直接做 DPO 会丢失 SFT 教会的参数映射

`dpo_joint`（从基座）68.5% vs SFT 83%：**33 个任务出现退化，全部是 `flight_search`**
（中文城市名 → 三字码、相对日期 → 绝对日期这类映射）。
DPO 只教「哪个回答更好」，不教这些**知识性映射**。

## Q3 「你怎么确定 83% 不是评测太松？」★这题答好最加分

**一句话**：我用**四种独立方式**验证过评测的严格性，而且**其中一次推翻了我自己的 95%**。

### 验证 1：agent 评测去掉了脚手架

单轮评测会把任务里**预计算的 observation** 注入 prompt（等于给答案）。agent 循环**不给**：

```
单轮：turn0 + turn1的observation + turn2  → 模型读答案后直接 book_flight
agent：只有 turn0                          → 模型必须自己 search → 读返回 → 再 book
```

**结果**：模型在 agent 循环里 100% 成功、恰好 2.00 轮 —— 证明它**确实会自己取信息**。

### 验证 2：主动查数据污染，结果推翻了自己的主结果

我做了污染检查，发现**训练数据里混入了评测任务**：

```
sft_only 训练样本 2509 条
其中 prompt 与评测 prompt 逐字相同: 1292 条（51.5%），且 chosen 就是正确答案
```

**这是我主动查出来的，不是别人指出的。** 重训后的干净数字是 **78.75%**（后来补语料覆盖到 83%）。

**量化了污染的影响**：

| 组 | 污染版 | 干净版 | 变化 |
|---|---|---|---|
| `seen`（训练见过） | 94.0% | 76.1% | **−17.9pp** |
| `unseen`（训练未接触） | 97.0% | 84.1% | −12.9pp |

**`seen` 掉得比 `unseen` 多 5pp** —— 这正是「泄漏主要惠及 `seen` 组」的指纹。

**可能的追问**：「你第一次的污染检查为什么没查出来？」
**答**（这题很关键）：我比对的是 `task_id`，而偏好数据里的 `task_id`
在我当时的加载路径下是空的 —— 于是「重叠 = 0」是个假阴性。
**教训是：查污染必须比对 prompt 文本，不能比对 ID 元数据。**

### 验证 3：评分口径交叉检查

发现 `cancel_booking` 的 schema 强制要求 `reason`，但评测只评 `booking_id`。
**agent 模式下工具真执行，schema 校验生效** —— 所以 agent 评测比单轮多一层约束。

### 验证 4（反面）：我曾误判评测「太严」，也纠正了自己

我一度认为评分器的 `extra_fields` 没有 schema 白名单会**压低**准确率，
还说「误判占全部失败的 58.8%」。**查代码后发现我错了**：

```python
passed = (category == SUCCESS)             # 判定只走这里
subtype = "extra_param" if extra else ""   # extra_fields 只设诊断标签
lenient_matched → category = SUCCESS        # 多给字段时恒为 SUCCESS
```

**`extra_fields` 从不参与打分**，重评分后所有数字一字未变。

**教训**：判断一个字段是否影响打分，要看 `passed` 的赋值处，
不能从「它被列在错误报告里」推断。

## Q4 「SFT 和 DPO 的本质差别是什么？」★这题最能体现理解深度

**一句话**：**纯正例只能表达「该做什么」，无法表达「不该做什么」；
对比信号才能编码否定性约束。**

### 证据：`missing_reason_corrected` 这一格

场景：用户说「我不想要 BK9A4C6F 这个订单了」但**没说原因**，
而 `cancel_booking` 要求 `reason` 必填。正确行为是**追问**，不是编造原因。

| 模型 | 总体准确率 | 该错误被纠正后 |
|---|---|---|
| baseline | 50.25% | 4/4 改对 |
| **sft_only** | **95%（最好的）** | **0/4 改对 + 4/4 重复同一错误** ❌ |
| dpo_joint（从基座） | 68.5% | **4/4 改对** ✅ |

**总体最好的模型，在这一项上唯一失败。**

**为什么**：SFT 的训练数据全是正例（`chosen` = 正确调用）。
数据里只有「该怎么做」，**没有「此处不该调用」**。
DPO 的 `rejected` 侧才能承载这个否定信息。

> ### ⚠️ 上面这段的**证据强度被我高估了**（2026-10 修正）
>
> **1) 有效独立样本是 1，不是 4。**
> 这 4 个任务的**期望调用完全相同**（正确行为都是「不调用工具」），
> 所以在自己的统计口径里它们属于**同一个簇**。
> 「4/4」是**4 种触发方式**，不是 4 个独立证据。
>
> **2) 「0/4 → 4/4 不受 CI 宽度限制、是能力的从无到有」这个说法是错的。**
> 4 个二值观测的 Fisher 精确检验 **p ≈ 0.029** —— 勉强显著，
> 而且是在**事后**挑出这一格之后算的。
> 换 14 种触发方式重做（v3 已扩到 14 个 clarify 任务）才能让这条结实。
>
> **3) 仍然成立的部分**：方向在 **β=0.1 与 β=0.5 两次独立运行中复现**
> （不是单次侥幸），且机制解释是自洽的 —— SFT 的正例数据里
> **确实没有**「此处不该调用」的样本，而 DPO 的 `rejected` 侧有。
> 这条仍然是我认为最有价值的发现，**但它的强度取决于 v3 重跑，
> 而且必须按「1 个行为」而不是「4 个样本」来报告。**

**可能的追问**：「SFT 的 `repeat_rate` 呢？」
**答**：SFT 的 `repeat_rate = 75%` —— 被纠正后仍有 3/4 概率再犯同一错。
它 91.7% 的 `recovered_rate` 主要来自「形式上改正了」，不是真的不犯了。
（同样受上面 1) 的限制：分母是触发方式数，不是独立样本数。）

## Q5 「DPO 在你项目里到底有没有用？」

**答案**：**总体上没有赢过 SFT，但在一个子能力上是唯一解。**
而且这个结论的强度受限于**评测规模**，不受限于方法本身。

**分三层说**：

| 层面 | 结论 |
|---|---|
| 总体准确率 | ❌ DPO 两组都低于 SFT（68.5% / 10.0% vs 83%） |
| 追问边界（`missing_reason`） | ✅ **DPO 4/4，SFT 0/4** —— 唯一能做到的 |
| 统计判定 | 100 任务下总体提升**不可能**被检出（14pp 门槛 > 17pp 天花板） |

**我把这个关键实验做完了，落在我预设的第三种结果上：**

### `dpo_sft_v3_b05`（β=0.5、lr=1e-5、1 epoch，从 sft_v3 83% 出发）

| 指标 | sft_v3 | **dpo_sft_v3_b05** |
|---|---|---|
| accuracy | 83.00% | **49.25%**（−33.75pp） |
| 格式正确率 | 100% | **58.8%** |
| `multi_tool` | 100% | **33.3%** |
| `booking_flow` | 72.2% | **16.7%** |
| `clarify_instead` | 20 | **54** |
| **`missing_reason_corrected`** | **0% 通过** | **100% 通过 / 0% 重复** ✅ |

**结论：对比信号能改善行为边界，但以损害任务执行能力为代价。**

**这个实验还暴露了一个训练监控盲区**（我在训练后判断错了）：

| 指标 | β=0.1 | β=0.5 |
|---|---|---|
| 终点 `logps/chosen` | −25.09 ❌ | **−4.55** ✅ |
| 我当时的判断 | 崩塌 | **「明显更健康」** |
| 实际 accuracy | 10.0% | **49.25%** |

**`logps/chosen` 稳定，任务能力依然崩掉 33.75pp。**
它只能预测「分布是否漂移」，**不能预测「任务能力是否保留」** ——
两者可以独立失效，而且后者不会在 `loss`、`margins`、`accuracies`、
`logps/chosen` 任何一个指标上留下痕迹。

**下一步该做什么**（如果继续这个方向）：需要的是**条件化的偏好数据**
（明确标注「在什么输入特征下 A 优于 B」），而不是更多同类偏好对。

## Q6 「说说你踩过的坑」★这题是加分题

**挑这个讲 —— 它同时展示了「发现问题的能力」和「承认错误的态度」**：

### 坑 1：评测设置错了两次，一次差 41pp

实现 agent 循环时，我改了「消息播种」逻辑，结果：

| 播种策略 | 成功率 | `booking_flow` | `cancellation` |
|---|---|---|---|
| 只播首轮（正确） | **94.87%** | 80.0% | 100% |
| 播所有 user 轮 + assistant 轮 | **53.85%** | **0%** | **0%** |

**同一个模型、同一个 adapter，只改播种，差 41 个百分点。**

**错在哪**（这两条推理我写进了代码注释和测试）：

1. **播了后续 user 轮** —— `task_0023` 的 `turn2` 是「就订 MU1000 这一班吧」，
   而 **`MU1000` 只有模型自己调 `search_flights` 才能知道**。
   提前播出去等于泄露答案 → 模型跳过搜索直接下单 → 10 条 `booking_flow` 全 0%。
2. **播了 20 个 assistant 预设轮** —— 那些是**目标动作的参考输出**，
   不是模型已看到的输入。播进去造成「模型没说过那句话，用户却回应了它」
   的不连贯 → 8 条 `cancellation` 全 0%。

**教训**：agent 评测的播种必须严格对齐「评测发生在对话的哪个时刻」。
我把它固化成 `test_agent_seeding_does_not_leak_future_turns`，**正反两个方向都断言**。

### 坑 2：数据污染，我自己查出来并推翻了主结果

见 Q3 验证 2。**从 95% 到 78.75% 再到 83%（补语料覆盖后）。**

### 坑 3：顺带查出的三个数据覆盖缺陷

修掉污染后暴露出（它们之前全被污染掩盖）：

| 缺陷 | 实测症状 | 修复 |
|---|---|---|
| 机场码只覆盖 13/20 | `flight_search` 59.1%，模型**编造三字码**（`CSX`→`CCN`、`SYX`→`SXM`） | 覆盖 20/20 → 68.2% |
| cancel 语料是单轮的 | `cancellation` 58.3%，20/48 是 `promise_only`（只说「我将为您取消」不调用） | 补确认轮结构 → 66.7% |
| book 样本带可选参数 | 模型把可选参数学成必填 | 只给必填参数 |

**这一类缺陷的共同特点：不报错、数字看起来正常、但结论是错的。**

### 坑 4：一次误判，也纠正了

见 Q3 验证 4 —— 我说评分器口径压低了准确率，查代码后发现 `extra_fields`
只影响诊断标签，不改 `passed`。

**我会主动说出这个，因为它证明我不会把「看起来是 bug」直接当结论。**

## Q7 「这个项目的局限是什么？」

**四个，都提前想好**：

1. **100 任务规模不够** —— CI ±10pp、可检出最小效应 14pp。
   要检出 5pp 级别的差异需要**约 400 任务/组**。
2. **agent 评测有覆盖度缺口** —— 39 个多轮任务**不含 `flight_search`**
   （单轮里最弱的 68.2%）。所以 agent 的 100% **只说明「与 agent 循环相关
   的四类都过关」，不代表整体**。
3. **DPO 未在干净数据上重跑** —— 两组 DPO 用的是含评测任务的旧数据，
   「DPO 没赢过 SFT」这个结论方向大概不变，但**绝对值不可引用**。
4. **`seen`/`unseen` 维度不可用** —— `seen` 反而比 `unseen` 低 16.3pp，
   而两组的类别与难度构成是均衡的（已核查）。说明该划分掺入了
   未识别的难度因素，**不能作为泛化指标**。

---

## Q8 「如果重做一遍，你会怎么改？」

1. **先建污染检查，再训第一个模型** —— 用 prompt 逐字比对，
   而不是比 `task_id`。这次是事后才发现，浪费了一轮 GPU。
2. **把合成语料的覆盖度做成自动检查** —— 断言「评测用到的每个工具、
   每个实体值（机场码/城市名）都在训练语料里出现过」。
   这次三个覆盖缺陷都是手工查出来的。
3. **任务集先扩到 400** —— 100 任务的 CI 太宽，很多结论只能停在
   「方向一致、统计不显著」。
4. **DPO 先做 β 扫描** —— 用 1/10 数据扫 3 个 β，再全量跑。
   β=0.1 直接崩掉浪费了一轮。
