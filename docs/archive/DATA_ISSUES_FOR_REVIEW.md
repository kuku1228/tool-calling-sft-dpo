## 2. 已修的三个致命问题

### 2.1 数据污染（已修）

**发现**：`sft_only` 的 2509 条训练样本里，
**1292 条（51.5%）的 prompt 与评测 prompt 逐字相同**，且 `chosen` 就是该任务的
正确答案 —— 等于在测试集上做梯度下降。

**根因**：不是「忘了过滤」，而是**注释与代码不一致**。
同一文件里 `build_recovery_pairs` 的文档写着

> 「不用评测集里的 recovery 任务…**评测与训练因此完全分离**」

**而它确实做到了** —— 只有它做到了。另外三处构造器
（`build_format_pairs` / `build_param_pairs` / `build_tool_selection_pairs`）
直接吃了 `pool = 评测任务 + 合成任务`。
**那句正确的注释让所有人（包括我）停止了核对。**

**修法（四层）**：
1. 前缀分界常量 `EVAL_TASK_PREFIX = "trainsyn_"`
2. `build_all` 硬门禁 —— 越界即 `raise`，报错信息里写明「会让全部结论作废」
3. 默认值 `tasks=[]`（忘记传参也不会污染）
4. 5 条回归测试（含「硬门禁必须真的抛错」）

**验证**：
```bash
python -c "
import sys; sys.path.insert(0,'.')
from src.data.recovery_corpus import assert_training_covers_eval_entities
print(assert_training_covers_eval_entities())
"
```

### 2.2 训练语料机场码覆盖不足（已修）

**发现**：机场码有**两份独立来源** —— `tool_catalog`（20 城）与
`task_manifest_v2`（60 城）。**训练语料读前者、评测读后者**，
于是 v3 需要的 52 个码里 **33 个模型从未见过**，
`flight_search` 上**必然编造**三字码（实测编出 `CCN`/`SXM`/`HTX`）。

**这是静默漂移**：不会报错，只会在评测时表现为「某一类莫名很低」。

**修法**：收敛到单一来源（`tool_catalog`），加断言
「评测需要的每个码，训练必须见过」。

**修的过程中又暴露两个问题**（都记在代码注释里）：
* `_ROUTE_PAIRS` 是**导入时算死的常量** —— 机场池扩了它不跟着变
* 「与评测撞车」过滤会**删掉航线任务**，而覆盖若只靠单条航线就会断
  （实测 `SYX` 因此一个训练样本都不剩）→ 改成两阶段选择
  （阶段 1 硬要求「每码至少 1 条」，阶段 2 补冗余）

## 3. 未修的问题（**请专家重点看这条**）

### 3.1 `seen`/`unseen` 标签**没有含义**

**判据是从不读取训练数据**：

```python
# v1：按序号轮转
visibility = "unseen" if self._counter % 3 == 0 else "seen"

# v2/v3：按骨架哈希
def _is_unseen(k): return sha256(k) % 3 == 0
```

它假设「合成训练语料只覆盖评测分布的一部分」。

**而我为了修 2.2（机场码未见），把合成语料扩到覆盖全部 60 个机场码 ——
于是这个假设被我自己的修复破坏了**：

```
seen   组签名被训练覆盖: 67/68 (99%)
unseen 组签名被训练覆盖: 38/38 (100%)   ← unseen 也 100% 见过
```

**后果**：`seen` vs `unseen` 的差值**不是泛化差距**，而是哈希分组的噪声。

**为什么我没修**：改成「按真实训练暴露分层」会变成 85 seen / 21 unseen，
**极度不平衡**，而且「seen」那一侧本身就有 §4 的泄漏问题。

**我目前的处置**：加了一个检查器，每次评测自动打印

```
⚠️ visibility（seen/unseen）标签在当前配置下没有含义：
   unseen 组签名被训练覆盖: 38/38 (100%)
   不要把 seen 与 unseen 的差值解释为泛化差距 —— 那是哈希分组的噪声
```

**请专家判断**：是应该
(a) 直接删除 `visibility` 概念，
(b) 重新定义成「重合层级」（见 §4），
还是 (c) 有其他更好的分层方式？

## 5. 未清表述：15 个 clarify 任务的有效样本是 **1**，不是 15

这是我自己做的一个**统计错误**，影响核心论点的强度。

**事实**：
```
clarify 任务 15 个，但期望调用只有 1 种（都是 {}）
→ 有效独立样本 = 1 个「行为」
→ 15 是**触发方式**的数量，不是独立证据的数量
```

**受影响的表述**（旧文档里）：

> 「`missing_reason` 上 SFT **0/4**、DPO **4/4** —— 证明否定性约束只能由
> `rejected` 侧承载」

**这条的问题**：
1. 有效样本是 **1 个行为**，4 是触发方式数
2. 「0/4 → 4/4 不受 CI 宽度限制、是能力的从无到有」这个说法**是错的** ——
   4 个二值观测的 Fisher 精确检验 p ≈ 0.029，勉强显著，
   而且是在**事后**挑出这一格之后算的

**仍然成立的部分**：方向在 **β=0.1 与 β=0.5 两次独立运行中复现**
（不是单次侥幸），机制解释也自洽（SFT 的正例数据里确实没有
「此处不该调用」的样本）。**但强度取决于 v3 重跑。**

**已做的处置**：统计口径改成**按簇重采样**
（`paired_stats.py` 里 `expected_keys` / `paired_bootstrap_clustered`），
实测有效样本从 101 降到 87、置信区间**变宽**（这是更保守的口径）。

**未做的处置**：旧文档里的「4/4」表述还没全部清掉。

## 6. 两个设计取舍（不是缺陷，但必须声明）

### 6.1 `search_flights` 占训练语料 48.6%

```
search_flights    88 (48.6%)
(clarify/空)      20 (11.0%)
book_flight       19 (10.5%)
check_baggage     18 (9.9%)
modify_baggage    15 (8.3%)
get_weather       13 (7.2%)
cancel_booking     8 (4.4%)
```

而**评测里 `search_flights` 只占 30%**。这会让模型的动作先验偏向搜索工具。

**我试过压到 30%，但会让 5 个机场码一条航线都没有**（覆盖断裂）。
覆盖断了是**确定性失败**（那些任务必然错），分布偏了只是**先验偏差**，
所以我选了覆盖面。**请专家判断这个取舍是否合理。**

### 6.2 DPO 数据里 clarify 仅占 13.7%

```
error_recovery    1013  (45.8%)
format_constraint  894  (40.4%)
clarify_boundary   304  (13.7%)   ← 核心论点所在，样本量最小
```

而且 C1 剂量实验的 100% 剂量要从 304 条凑到 1000 条
→ **有放回重采样**（同一数据被多次见到），这会放大该方向的梯度信号。
脚本会打印标记，报告里必须写明。

### 6.3 SFT 训练数据含 0 条否定样本 —— 但这**不是缺陷**

```
sft_only 共 2563 条，chosen 不含 tool_call 的: 0 条 (0.0%)
```

我原以为 SFT 学不会「信息不足要追问」是因为**数据缺这类样本**。
但查了 prompt 后发现**规则就写在系统提示里**：

```
【输出格式 —— 最重要，必须严格遵守】
...
4. 信息不足时先向用户追问，不要臆造参数。
5. 如果不需要调用工具，直接用自然语言回复用户。
```

**所以这不是「没被告知」，是「指令遵循失败」。**

**这反而加强了我的论点**：它排除了「模型不知道要这么做」这个解释。
而且它意味着 SFT vs DPO 的对比**不是不公平的**
（不能说「SFT 因为数据里没有所以做不到」—— 它有指令）。

**但这个发现也带来一个新问题**：既然规则在 prompt 里，那么
