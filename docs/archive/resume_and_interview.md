## 二、面试问答

### A. 概念题（必考）

#### A1. DPO 和 SFT 的区别是什么？

**要点**：不是「新方法 vs 旧方法」，而是**监督信号的性质不同**。

- SFT 最大化 `log π(y_w | x)`，只告诉模型「这个答案是对的」。所有 token 被同等强化。
- DPO 最大化 `log σ(β · [(log π_θ(y_w) − log π_ref(y_w)) − (log π_θ(y_l) − log π_ref(y_l))])`，告诉模型「y_w **比** y_l 好」。信号来自**对比**，而且用 reference model 做锚点，防止偏离过远。

**关键推论**：SFT 在「正确答案的分布」之外没有信息。DPO 的对比结构让它可以表达「两个都不完美，但哪个更好」——这在工具调用里很关键，因为很多失败的输出格式都是合法的，只是内容错。

**可补充一句**：DPO 不需要单独训练奖励模型，这是相对 PPO/RLHF 的主要工程优势；代价是无法像 RL 那样探索训练分布之外的行为。

#### A2. DPO 的损失函数怎么推导？

按这四步讲，不要跳步：

**第一步**：RLHF 的目标是在奖励和 KL 约束之间平衡

```
max_π  E_{y~π}[r(x,y)]  −  β · KL(π(y|x) ‖ π_ref(y|x))
```

**第二步**：这个目标有闭式最优解（用变分法或直接配分函数）

```
π*(y|x) = (1/Z(x)) · π_ref(y|x) · exp(r(x,y)/β)
```

**第三步**：反解出隐式奖励

```
r(x,y) = β · log(π*(y|x) / π_ref(y|x)) + β · log Z(x)
```

**第四步**：代入 Bradley-Terry 偏好模型 `P(y_w ≻ y_l) = σ(r(y_w) − r(y_l))`。配分项 `β log Z(x)` 在差值里**抵消**（这就是为什么 DPO 不需要估计配分函数，也是它优雅的地方），得到

```
L = −E[ log σ( β·[(log π_θ(y_w) − log π_ref(y_w)) − (log π_θ(y_l) − log π_ref(y_l))] ) ]
```

**面试官常追问的点**：
- 「这个推导的关键假设是什么？」→ Bradley-Terry 模型，即偏好概率只由奖励差决定；以及最优策略的闭式解存在（KL 正则保证了这一点）。
- 「配分函数为什么能消掉？」→ 因为它只依赖 x，与 y 无关，在同一个 x 下的两个 y 相减时抵消。
- 「这和 PPO 相比丢了什么？」→ 丢了在线探索。DPO 是离线方法，只能学到偏好数据覆盖到的区域。

#### A3. β 参数的作用是什么？

**三个层次，按深浅讲**：

**层次一（物理含义）**：β 控制对 reference model 的偏离惩罚强度。
- β → ∞：完全不动，退化为 reference model 本身
- β → 0：完全放开 KL 约束，退化为纯 Bradley-Terry 拟合

**层次二（对损失的影响）**：β 出现在 margin `z = β·(…)` 里。
- β 大 → z 被放大 → `−log σ(z)` 更小 → **损失值看起来更好**
- 但注意：`π_θ = π_ref` 时 z 恒为 0，损失恒为 `log 2 ≈ 0.693`，与 β 无关

**层次三（这个最容易被忽略，也最能体现理解深度）**：β 同时出现在**梯度**里。

```
∂L/∂ log π_θ(y_w) = −β · σ(−z)
∂L/∂ log π_θ(y_l) = +β · σ(−z)
```

所以 β 小的时候，虽然 margin 可能更大（损失更小），但**梯度幅度也被 β 线性缩小**。这意味着 **β 和 learning rate 必须一起调**，只改一个会得到误导性的结论。

**实证取值**：DPO 论文主实验用 β=0.1（batch 64、RMSprop、lr=1e-6、150 步 warmup），摘要任务用 β=0.5。TRL 的 `DPOConfig.beta` 默认 0.1。

#### A4. 为什么用 LoRA 而不是全参数微调？

- **显存**：1.5B 全参微调需要存梯度 + Adam 的一阶二阶动量，约 20GB+；LoRA 只训练 adapter（r=16 时不到 1% 参数），8GB 级别
- **可复用**：一个基座 + 多个 adapter，做消融实验时不用为每个实验存一份完整模型（这对「跑四组对比」的场景是刚需）
- **抗过拟合**：偏好数据只有几千条，全参微调容易过拟合

**但要主动说清一个陷阱**（这个能体现你真跑过）：

`ref_model=None` + PEFT 时，TRL 通过 `model.disable_adapter()` 计算 reference logprob。此时 **reference 就是原始 base 模型**。

后果：如果你先在 base 上做 LoRA SFT，然后**继续用同一个 adapter** 做 DPO，那么 reference 是 base，而 policy 是 base+SFT+DPO——KL 锚点被拉得很远，DPO 会过度偏离，训练不稳。

正确做法是先把 SFT adapter merge 进 base、保存成新模型，再在新模型上新建 LoRA 做 DPO。我在训练脚本里加了 `--init-adapter` 参数实现这条路径。

#### A5. 为什么用 pass^k 而不是 accuracy？

**核心论点**：小模型的行为特征是「飘」，不是「稳定的对或稳定的错」。

同一个任务采样 4 次可能对 2 次错 2 次。用单次准确率衡量，「4 次全对 2 次任务 + 4 次全错 2 次任务」和「4 次对各 2 次」的模型看起来完全一样（都是 50%），但可用性完全不同。

**定义与实现**：

```
pass@k = 1 − C(n−c, k)/C(n, k)     至少一次成功
pass^k =     C(c,   k)/C(n, k)     k 次全部成功
```

**关键细节（体现严谨性）**：不能用朴素的 `(c/n)^k`。那个式子把「从同一批样本里取 k 个」当成「独立重采 k 次」，在 n 小时有偏。n=4, c=2, k=2 时朴素给 0.25，无偏给 1/6 ≈ 0.167，差 50%。

**还要说清一个退化情形**：τ-bench 报 pass^4 时 n 通常就等于 4，此时 `C(4,4)=1`，无偏估计退化成 0/1（要么 4 次全对要么不是）。我在报告里同时给一个有偏的 `(c/n)^k` 作为参考，并明确标注它是有偏的，主指标仍用无偏形式。

**最后给一个我实际用的衍生指标**：`Δstability = pass^k − pass@k`。它衡量「会做但不稳」的程度，越接近 0 越好。这是我认为比单一准确率有意义得多的一个数。

#### A6. 你的评测怎么保证可信？

分四层讲：

1. **语义等价而非字符串匹配**：`2025-07-15` vs `2025/7/15`、`PEK` vs `北京`、`30` vs `"30公斤"` 都判为等价。否则「答对了但写法不同」会产生大量假阳性，污染指标。
2. **两套口径同时报告**：严格口径（全部期望参数命中）+ 宽松口径（只比对关键字段）。如果宽松涨了而严格没涨，说明模型学了「关键字段对、细节不管」的捷径——这个信号必须可见。
3. **置信区间用任务级 bootstrap**：重采样单位是**任务**而不是采样样本。同一任务的多次采样高度相关，按样本重采样会严重低估区间宽度。
4. **统计功效估算**：用 `required_sample_size(effect)` 反推要检出观测到的效应需要多少个任务。如果当前任务数不够，就明确说「观测到的提升可能不稳定」，而不是直接宣称成功。

### B. 项目深挖题

#### B1. 你的偏好对是怎么构造的？

分四类讲，每类说清 chosen/rejected 的来源：

| 类型 | chosen 来源 | rejected 构造 |
|---|---|---|
| 格式约束 | 任务 ground truth 直接构造 canonical 调用 | 纯文本承诺 / 键无引号的坏 JSON / markdown 围栏 |
| 工具选择 | 同上 | 命名变体假工具（`find_flights`）/ 语义相邻的真实工具 |
| 参数约束 | 同上 | 占位符（`previous_booking`）/ 换一个字符 / 错格式 |
| **错误恢复** | 纠错后的正确调用 | 原样重复首轮错误 / 退化成纯文本 / 换错工具 |

**补充说明为什么不用大模型生成 chosen**：原规划是用 72B 生成，实际改成从 ground truth 构造。好处是完全可控、可复现、零 API 成本；代价是 chosen 的自然度不如大模型生成。在这个规模上我选了可复现性。

**如果被问「rejected 怎么保证有区分度」**：这就是硬负样本比例（0.35）的作用。全用「一眼假」的负样本，模型不需要理解工具语义就能区分，训练信号几乎为零。真正有价值的是**格式完全正确、只是实体错一个字符**的硬负样本。

#### B2. 为什么「错误恢复偏好对」有效？

**这是本项目的核心卖点，要讲透。**

论证链：
1. SFT 的 chosen 里**只有正确答案**，模型无从学到「先错后改」这个模式——数据里根本没有。
2. 但真实 Agent 交互中，用户纠错是**高频事件**。一个不会改错的 Agent 实际上不可用。
3. 所以我在偏好对的 **prompt 里显式包含了「模型首轮的错误回复 + 用户的纠错话术」**，chosen 是修正后的回复，rejected 是原样重复。

这样 DPO 的对比信号直接作用在「面对纠错时该怎么反应」这个决策点上。

**可以加一句工程细节**：这个设计对数据构造有额外要求——纠错话术必须与首轮错误**语义连贯**。我早期版本从话术池随机抽句子，生成了「航班搜索场景 + 『city 参数要填中文城市名』」这种自相矛盾的数据，它会教模型忽略用户纠正。所以加了 `_recovery_coherence` 门禁：话术里提到的参数必须真的出现在首轮错误调用的参数里。

#### B3. 你怎么评测工具调用的对错？

三个层面：

1. **格式**：是否有唯一一处合法的 `<tool_call>` 标签包裹标准 JSON（`is_canonical_format`）。注意这和「任务是否成功」是**独立**的两件事，必须分开报告。
2. **工具名**：精确匹配白名单。不在白名单 → 幻觉。这里细分两类：命名变体（`find_flights`）和完全无关（`search_hotel`），因为前者才是小模型的典型幻觉形态。
3. **参数**：字段级语义等价比对，两套口径（严格/宽松）。同时统计字段级准确率（`param_accuracy`），比二元判定更能看出趋势。

**补充一个细节**：解析器不做「猜测补全」。例如 `{name: get_weather}` 这种缺引号的片段，**不**试图猜成一个合法调用，而是记为 `json_broken`。猜错比不猜更危险——它会让评测指标虚高。

#### B4. 实验中遇到的最大坑是什么？

**推荐讲「成功概率与错误率脱钩」这个，因为它最隐蔽、也最能体现方法论思考。**

现象：我在 mock 流水线里把格式错误率降低 65%，但各实验的准确率指标**纹丝不动**。

排查过程：
1. 先怀疑注入没生效 → 加了注入一致性自检（比较「想注入的错误类型」与「评分器判出的类别」），发现一致性正常
2. 再怀疑评分器有问题 → 单独跑评分器，正常
3. 最后看概率模型才反应过来：我把「成功率」和「各类错误的相对权重」**独立设定**了

根因：降低格式错误只是把概率质量从「格式错误」挪到「其他错误」，成功率作为独立参数不受影响。

修法：让成功成为补集 `p_success = 1 − Σ p_err(e)`。改完之后四个实验立刻产生了可区分的差异（基线 51.5% → 联合方案 78.8%）。

**升华一句**：这个坑的本质是「改了自变量但目标量对它不敏感」。**建模时必须先验证「改动能传导到目标量」，否则实验设计是空的**——你会跑完四组实验才发现它们本该没有差异。

**备选答案**（如果面试官想听工程坑）：纠错话术与错误类型不匹配那个（见 B2），危害更大但更容易解释。

#### B5. 你怎么保证提升不是噪声？

四点：

1. **任务级 bootstrap 置信区间**（1000 次重采样任务），判断处理组与基线的 CI 是否重叠。重叠就不能断言有真实提升。
2. **效应量**：用 Cohen's h 量化比例差异，避免「提升 0.5% 但 p<0.05」这种统计显著但实际无意义的结论。
3. **样本量反推**：`required_sample_size(effect)` 给出要检出该效应需要的任务数。如果当前 100 个任务不够，需在报告中说明。
4. **混淆因素排查**：这是最容易被忽略的一层。我专门设计了几个对照组排除替代解释：
   - 提升是否只来自更啰嗦的 system prompt？→ `--lite-system` 跑一遍
   - 提升是否只来自工具选择空间变小？→ `--tools` 限定工具集
   - 提升是否只来自能看见工具返回结果？→ `--no-observations`
   - **提升是否只来自更多监督数据量而非对比信号？→ `sft_only` 对照组**

#### B6. 如果只用 chosen 做 SFT 就能达到同样效果，你的项目还成立吗？

**这是最锋利的问题，必须正面回答，不能躲。**

答：**那我的核心论点就不成立，而我把这个可能性做成了实验矩阵的一部分。**

`dpo_recovery` 的卖点是「对比信号是必要的」。要支撑这个论点，需要一个反例：如果 SFT 也能达到同样效果，提升就来自「更多监督数据」而不是「对比学习」。

所以我加了 `sft_only` 对照组，而且它的数据**有意不含错误恢复对**——理由是恢复能力无法由「只有正确答案」的数据教出来，这正是要被检验的假设。

如果 SFT 组在恢复率上也涨了，说明论证链有问题，结论需相应改写。

**可以再补一句**：我认为实验设计里必须留一条能推翻自己的路径，否则就是在给自己写结论而不是做研究。

#### B7. 这个项目有什么局限？

主动列，不要等面试官挤：

1. **评测集是自建模板化的**。纠错话术来自模板池，不是真人。这会让「错误恢复率」的绝对值偏乐观——真实用户的纠错方式远比模板多样。要得到可跨项目比较的数字需要 τ-bench 那样带真实 user simulator 的基准，但那需要 72B 级模拟器，超出单卡预算。
2. **主评测是单轮口径**（给定确定的多轮前缀评一轮），忽略了多轮累积误差。补偿措施是另写了一个走真实多轮、专测恢复率的 `eval_recovery.py`。
3. **1.5B 的天花板**。即便 DPO 生效，绝对准确率也不会高。本项目论证的是**相对改善**与**方法有效性**，不是「小模型能生产可用」。
4. **偏好数据的 chosen 是构造的而非大模型生成的**，自然度有偏差。
5. **mock 流水线只证明代码能跑，不证明方法有效**。这两件事必须严格区分。

### C. 可能的追问与陷阱题

#### C1. TRL 里 `loss_type="simpo"` 怎么用？

**这是陷阱题，正确回答是：TRL 的 `DPOTrainer` 从来没有支持过 `simpo`（也没有 `orpo`）。**

- SimPO 在 TRL 里走 `CPOTrainer`
- ORPO 有独立的 `ORPOTrainer`
- `DPOConfig.loss_type` 实际支持的是 `sigmoid` / `hinge` / `ipo` / `kto_pair`（0.9 起移除）等

**主动说**：「网上很多教程写 `loss_type='simpo'`，那是错的」——这个回答能立刻区分出你是真读过源码还是抄的教程。

#### C2. `max_prompt_length` 在新版 TRL 里还能用吗？

有明确的时间线：

- **≤ 0.13.0**：正常可用，默认 512
- **0.28.0**：弃用，默认改成哨兵值 `-1` 并给 FutureWarning
- **0.29.0**：从 `DPOConfig` 完全移除

所以 **0.14 ~ 0.27 是「`max_length` 与 `max_prompt_length` 双旋钮都可用」的窗口**。我的项目锁 `trl==0.13.0`，理由之一是它同时满足：`DPOConfig` + `processing_class` 已是推荐路径但旧名仍兼容、位置参数弃用恰好到期、双旋钮都正常。

#### C3. `tokenizer=` 和 `processing_class=` 该用哪个？

- **0.12.0** 新增 `processing_class`，同时弃用 `tokenizer`（源码里的装饰器标 `version="0.14.0"`）
- **0.14.0** 移除 `tokenizer`

所以 0.12/0.13 两个都能用，0.14+ 只能用 `processing_class`。我写了个兼容层用 `inspect.signature` 探测，而不是 `try/except TypeError`——因为 `TypeError` 可能来自内部（例如 `DPOConfig` 少个字段），被吞掉后会误判成「版本不支持新 API」，最终报出与真实原因无关的错误。

#### C4. 为什么 DPO 训练不稳定？怎么调？

按可能性排序：

1. **β 太大** → 模型不敢偏离 reference → 梯度小、学不动。先降 β（0.1 → 0.05）
2. **lr 太大** → DPO 梯度尺度与 SFT 不同（多乘了一个 β·σ(−z)），常见做法是比 SFT 小一个量级
3. **偏好数据两侧语义等价** → loss 恒为 log 2，梯度为零。这是我加「语义等价反查」门禁的原因
4. **截断导致两侧变得相同** → 同上。所以训练前必须做长度体检，报出「截断后退化率」
5. **reference 锚点错位** → 见 A4 的 SFT→DPO adapter 陷阱

**监控什么**：`rewards/margin`（隐式奖励差）应该单调上升；`rewards/accuracy`（chosen 的隐式奖励高于 rejected 的比例）应该在 0.5 以上并上升；loss 从 `log 2 ≈ 0.693` 开始下降。如果 loss 一直贴着 0.693 不动，几乎一定是数据问题。

#### C5. 你这个项目为什么不做 online RL（PPO/GRPO）？

回答是**成本约束下的工程选择**：

- GRPO 需要在线 rollout。多轮工具调用的一次 rollout 要跑完整对话，成本与对话轮数成正比
- 对标项目用 7B policy + 72B user simulator + 2×A800，每方案 300 step 约 70 小时
- 我在单卡 24G 的预算下，四周内不可能跑完四组消融

DPO 是离线方法，训练成本与对话轮数**无关**，这是能在预算内完成的唯一路径。

**但要主动说清代价**：DPO 无法探索偏好数据覆盖不到的区域。如果偏好数据里没有「用户连续纠错三次」这种场景，模型就学不会。这是离线方法的固有局限。

#### C6. 你的评测集只有 100 个任务，够吗？

**不要只说「够」或「不够」，要给量化依据。**

答：这取决于要检出的效应量。用两比例比较的样本量公式反推，在 80% 功效、α=0.05 下：

- 要检出 20 个百分点的提升 → 约需 50 个任务
- 要检出 10 个百分点 → 约需 190 个任务
- 要检出 5 个百分点 → 约需 780 个任务

所以 **100 个任务对「大幅改善」是够的，对「细微改善」是不够的**。我在汇总脚本里实现了这个反推，报告会明确写出「观测到的提升是否在可检出范围内」，并在样本量不足时标注提升可能不稳定。

**加分的一句**：这也是我为什么把 `pass^k` 和 `accuracy` 都报——`pass^k` 的估计方差比 `accuracy` 大（它是对同一批样本的更严格函数），在任务数不足时更容易出现大幅波动，需要额外注意。
