## §1 简历条目（可直接粘贴）

### 航空客服工具调用 Agent 的评测体系与训练语料优化

**个人项目** ｜ 2026 ｜ 技术栈：Python / PyTorch / Transformers / TRL / LoRA / Qwen2.5-1.5B

**项目背景**：在垂直领域（航空客服）构建工具调用 Agent 的完整优化与评测闭环，
目标是解决小模型在「何时调用工具、如何取参数」上的决策不可靠问题。

**主要工作与成果**：

- **独立搭建工具调用评测基准与训练流水线**：自建 **106 任务**基准
  （8 类，覆盖多步流程、多工具组合、跨轮改主意、错误纠正），
  逐任务错误分类体系（**7 类互斥 + 子类型细分**），偏好数据构造器，
  SFT/DPO 训练与单轮/多轮双轨评测。任务集约束全部可自动化检查
  （骨架/任务比 **0.99**、实体唯一、跨类别无重合）。

- **将 Qwen2.5-1.5B 的准确率从 28.0% 提升至 95.3%**（106 任务 × 4 采样，
  pass^4 ~93%）。其中三个类别从 **0% 提升至 93~100%**。

- **发现并修复了一个会虚高准确率的评分漏洞**：定位到「应先追问」类任务的
  判据仅检查"未调用工具"，导致**空输出被判为正确** —— 未训练基座因此在该类
  任务上"通过 98.2%"，使总体准确率虚高 **14 个百分点**。修正后真实基线为
  **28.0%**（91 个需调用工具的任务）。该发现对同类评测具有通用性。

- **诊断并修复了训练语料的"技能缺口"**：语料已覆盖全部 52 个机场码
  （实体覆盖检查全绿），但**带工具观测的多步任务为 0、多工具任务为 0**，
  而评测有 **31 个任务**依赖这两项技能，导致三个类别准确率为 0%。
  补齐后（语料 **181 → 247** 任务）提升至 93~100%；其中 `flight_search`
  未经专项补数据也升至 100%，验证了技能迁移。

- **通过受控实验确立失效机制**：证明 **SFT 学到的是"全局决策倾向"而非
  "条件规则"**。在同一模型、同一任务集、同一超参下，仅调整训练数据中
  "不应调用工具"样本的**占比**（0.0% → 12.1%），决策边界任务准确率从
  **31.8% → 95.5%**，而需调用工具的任务保持 ~95%。该占比与评测分布匹配
  （12.1% vs 14.2%），排除了"数据量不足"的解释。

**核心能力标签**：评测体系设计 ｜ 数据质量审计 ｜ 失效归因 ｜ 小模型训练调优

## §2 面试展开版（按 STAR）

### S — 背景与目标

**领域**：航空客服场景的工具调用 Agent。用户用自然语言提出需求，
Agent 需决定是否调用工具、调用哪个、参数如何填。

**问题**：小模型（1.5B）的决策不可靠，具体表现为三个典型失效：
① 信息不足时凭空编造参数；② 有工具观测时不会读取；③ 多工具任务只完成一半。

**目标**：建立**可信的**评测基准，定位失效根因，并用最小改动修复。

### T — 我的职责

独立完成全流程：任务集设计 → 错误分类体系 → 训练语料构造 →
模型训练（SFT/DPO）→ 评测与统计分析 → 失效归因。

### A — 做法

**1. 先建评测可信性，再做实验**

这是我改变过的做法。最初我直接开始训练，结果所有结论都被推翻了两次
（数据污染、任务集缺陷）。后来我把顺序反过来：**先用可检查的约束
锁定评测集，再跑实验**。

任务集的每一条约束都写成断言 + 反向测试：

```
骨架/任务比 ≥ 0.9        订单号/乘客名/取消原因全局唯一
日期必须在未来            跨类别实体不得重合
期望参数不得为空          期望值必须能从给定信息推导
multi_tool 必须声明两个工具  训练语料必须覆盖评测所需的技能
```

**关键设计：给检查器本身写反向测试** —— 喂入已知坏数据，确认它真的报警。
因为「检查器写错了、永远返回通过」是这个项目里出现过的真实错误。

**2. 用受控实验区分「数据问题」与「模型能力问题」**

三个类别准确率为 0% 时，有两种可能：语料缺口 or 模型学不会。
我做的区分是：**补上对应的技能语料，看是否改善**。
补齐后升至 93~100% → 确认是数据问题，不是能力瓶颈。

**3. 用「仅改一个变量」的实验确立机制**

发现 SFT 数据里「不应调用」样本占 0% 后，我没有直接下结论，
而是构造了一个只差这个变量的对照：

| 实验 | 训练数据 | 「不调用」占比 | cancellation |
|---|---|---|---|
| `sft_only` | 2635 条 | **0.0%** | 31.8% |
| `sft_clarify` | 2999 条（+364 条追问） | **12.1%** | **95.5%** |

同模型、同任务集、同超参 → 行为翻转。且该占比与评测分布匹配
（12.1% vs 14.2%），排除"数据量不足"。

### R — 结果

| 指标 | 值 |
|---|---|
| 总体准确率 | **28.0% → 95.3%** |
| pass^4 | ~93% |
| 簇级口径 | ~94% |
| 三个 0% 类别 | 0% → 93~100% |
| 剩余失败 | 20/424（4.7%），其中决策类错误 **1/424** |

## §3 技术要点清单（面试可展开）

### 评测体系

- **8 类任务 / 106 个任务**：多步流程、多工具组合、真多轮（用户改主意）、
  错误纠正、应先追问、单轮查询
- **7 类互斥错误 + 子类型细分**：`SUCCESS` / `FORMAT_ERROR` / `HALLUCINATION` /
  `WRONG_TOOL` / `PARAM_ERROR` / `REFUSED` / `UNKNOWN`，
  子类型如 `adjacent_tool`（选错相邻工具）、`should_clarify`（该追问却调用）、
  `empty`（空输出）、`clarify_instead`（正确追问）
- **严格 vs 宽松口径**双判据（`strict_ok` / `lenient_ok`），
  区分「格式对但值错」这类 reward hacking 征兆
- **pass@k / pass^k / Δstability** 三个稳定性指标

### 统计方法

- **配对 bootstrap**（重采样单位是**任务**，不是样本 ——
  同任务多次采样高度相关）
- **McNemar 精确检验**（不用卡方：不一致对常 < 10）
- **MDE 功效分析**：实测 100 任务可检出最小效应 ≈ **14pp**，
  所以"差几个百分点"的结论在该规模下不成立
- **簇级口径**：106 个任务只有 92 个不同期望调用，其中一个簇 15 个任务
  期望完全相同 → 有效样本是**簇数**，不是任务数

### 数据质量审计（本项目的核心工作量）

发现并修复 **8 类"不报错但结论会错"的缺陷**：

| 缺陷 | 症状 |
|---|---|
| 训练数据含评测任务（51.5%） | 准确率**更高** |
| 空输出判为正确 | 基线虚高 14pp |
| 机场码两处漂移 | 33 个码模型从未见过 |
| 训练语料零多步任务 | 三类 0%，而实体覆盖检查**全绿** |
| 追问样本未进 SFT | 补了语料但 pair_type 不含，**白跑 30 分钟** |
| 期望值不可推导 | 任务**永远答不对**，被记成「模型参数错」 |
| 一致性检查器假通过 | 报「✓ 一致」但只比对了前 400 字符 |
| 循环导入 | 7 个测试**静默不注册** |

**共同点：全都不报错。** 数字正常、loss 正常、测试通过，而结论是错的。

### 工程实践

- **确定性**：哈希用 `hashlib`（不依赖 `PYTHONHASHSEED`）；任务集有 SHA256 指纹
- **门禁化**：`verify_all.py` 一条命令跑 6 项数据检查，失败即阻断
- **自动化产物**：每次评测自动生成「已知限制」清单，防止报告漏声明
- **195 个单元测试** + 全模块 doctest + 检查器反向测试
