# 基线诊断：Qwen2.5-1.5B 在工具调用任务上错在哪

> 数据来源：`experiments/baseline/eval_report.json` 与 `error_analysis.json`。
> 协议：106 任务 × 4 采样 = 424 次采样，温度 0.7，单卡 RTX 3090，未做任何微调。

---

## 1. 诊断目的与协议

### 1.1 要回答的问题

1. 未训练的小模型在工具调用上**整体能到什么水平**？
2. 失败集中在**哪几类**错误上？各自占比多少？
3. 这些错误是**能力缺失**还是**格式问题**？—— 两者的改进方向完全不同。

### 1.2 评测协议

| 项 | 值 |
|---|---|
| 任务集 | v3 冻结集，**106 任务 / 8 类别 / 3 档难度** |
| 采样 | 每任务 4 次，temperature = 0.7 |
| 主指标 | pass^k（k=1,2,4，无偏估计 `C(c,k)/C(n,k)`）+ Δstability |
| 判据 | 工具名精确匹配 + 参数语义等价（宽松口径为主，另报严格口径） |
| 工具集 | 白名单 6 个工具 |

### 1.3 为什么主指标用 pass^k 而不是 accuracy

单一 accuracy 会掩盖一个关键区别：**「能做对某题」与「每次都能做对」是两件事**。
对 Agent 类任务，后者才是部署关心的量：

```
pass@k  一个任务采样 k 次、至少一次对     → "它会不会做"
pass^k  一个任务采样 k 次、k 次全对       → "它稳不稳"
Δstability = pass^k − pass@k             → "会做但不稳" 的程度
```

> n=4、k=4 时 `pass^4` 退化为 0/1 两档（`C(c,4)/C(4,4) ∈ {0,1}`）。
> 报告同时给出有偏参考值 `(c/n)^k`，避免读者把"恒为 0"误读成 bug。

## 2. 整体结果

| 指标 | 值 | 95% CI |
|---|---|---|
| accuracy（单次采样） | **38.9%** | [30.7%, 47.6%] |
| pass@1 | 38.9% | [29.7%, 48.1%] |
| pass@2 | 41.7% | [32.7%, 50.5%] |
| pass@4 | 43.4% | [34.0%, 52.8%] |
| pass^1 | 38.9% | [30.9%, 47.9%] |
| pass^2 | 36.2% | [27.4%, 44.7%] |
| **pass^4** | **34.0%** | [25.5%, 43.4%] |
| **Δstability** | **−9.4%** | [−15.1%, −4.7%] |

### 2.1 这组数字说明什么

- **pass@4 只比单次准确率高 4.5pp**（43.4% vs 38.9%），**pass^4 只有 34.0%**。
  这说明：**模型答错的题，重采样 4 次基本还是错**；答对的题则稳定答对。
  这不是"随机犯错"，而是**确定性失败**——重采样换不来正确率。
- 因此当前主要矛盾是**能力覆盖**，不是输出稳定性。这个判断直接决定了改进方向
  应放在**训练数据与训练方式**上。

### 2.2 与后续实验的可比性锚点

基线是所有实验的参照系。后续每个实验都必须满足：

1. 任务集相同（v3，106 任务）
2. 采样次数与温度相同（4 次，0.7）
3. 评分口径相同（同一版 `grader.py`）

---

## 3. 错误分布

### 3.1 分类体系

7 个互斥类别，按优先级排列（先判格式可解析性，再判语义）：

```
SUCCESS → FORMAT_ERROR → HALLUCINATION → WRONG_TOOL → PARAM_ERROR → REFUSED → UNKNOWN
```

优先级理由：**JSON 都解析不出来时，讨论工具名对不对没有意义**。

### 3.2 分布（424 次采样）

| 错误类别 | 数量 | 占总样本 | 占失败 |
|---|---|---|---|
| 成功 | 165 | 38.9% | — |
| **格式错误** (`FORMAT_ERROR`) | **141** | **33.3%** | **54.4%** |
| **参数错误** (`PARAM_ERROR`) | **111** | **26.2%** | **42.9%** |
| 工具选错 (`WRONG_TOOL`) | 7 | 1.7% | 2.7% |
| 工具幻觉 (`HALLUCINATION`) | **0** | 0.0% | 0.0% |
| 拒绝 / 未知 | 0 | 0.0% | 0.0% |

**两个类别覆盖了 97.3% 的失败**：格式错误与参数错误。

### 3.3 失败子类型（Top）

| 子类型 | 数量 | 归属 |
|---|---|---|
| `promise_only` 只承诺要查、没真的调用 | 27 | FORMAT_ERROR |
| `no_tool_call` 完全没有 `<tool_call>` 标签 | 26 | FORMAT_ERROR |
| 其余格式错误子类型 | 88 | FORMAT_ERROR |
| 参数值错 / 缺参 / 占位符 | 111 | PARAM_ERROR |
| `should_clarify` 信息不足却直接调用 | 1 | WRONG_TOOL |

### 3.4 这份分布推翻的一个直觉

**工具幻觉为 0。** 未训练模型的问题不是"编造不存在的工具"，而是：

1. **不愿或不会输出合法的 `<tool_call>`**——141 条格式错误中，53 条是
   "只说不做"或"完全不输出标签"
2. **参数字段填不对**——111 条参数错误

这意味着"白名单记忆"这类担心在基线阶段并不成立；真正的瓶颈是**格式遵从**
与**参数正确性**。

## 4. 分组下钻

### 4.1 按难度

| 难度 | n | accuracy | pass@4 | pass^4 |
|---|---|---|---|---|
| easy | 24 | 77.1% | 87.5% | 66.7% |
| medium | 15 | 55.0% | 66.7% | 46.7% |
| **hard** | **67** | **21.6%** | 22.4% | 19.4% |

难度标签有区分度（easy 77.1% vs hard 21.6%），且 **67/106 的任务落在 hard**——
这解释了为什么整体准确率只有 38.9%。

> 难度标签当前按类别手工赋予。`scripts/eval/assign_difficulty_by_accuracy.py`
> 可按实测准确率重标，用于后续修订。

### 4.2 按类别

| 类别 | n | accuracy | 考察点 |
|---|---|---|---|
| `weather_advisory` | 10 | 90.0% | 参数语义区分（中文城市名） |
| `baggage` | 14 | 67.9% | 订单号格式、数值参数 |
| `cancellation` | 22 | 62.5% | 见 §4.3 警告 |
| `error_correction` | 15 | 55.0% | 用户纠错后自我修正 |
| **`multi_turn`** | 6 | **12.5%** | 跨轮参数更新 |
| **`flight_search`** | 14 | **0.0%** | 城市名 → 机场三字码 + 日期换算 |
| **`booking_flow`** | 15 | **0.0%** | 从工具观测读 `flight_id` 再下单 |
| **`multi_tool`** | 10 | **0.0%** | 一轮内串起多个工具 |

**三个类别为 0%**，共 39 个任务（占 36.8%）。

### 4.3 `cancellation` 的 62.5% 属虚假通过

`cancellation` 的 22 个任务里 **15 个是「信息不足，应先追问」**。原评分判据只检查
「有没有调用工具」，于是**空输出也被判为正确**：

```
'请问您取消的原因是什么？'  → 判为正确  ✅ 合理
'请提供订单号'              → 判为正确  ✅ 合理
''                        → 判为正确  ❌ 空输出
```

未训练模型几乎不调用工具，因此在 15 个追问任务上"免费"通过（实测 98.2%），
使该类别虚高。**该判据已修复**（空输出判失败，并新增按任务口径的格式正确率）。

**解读基线时应看 `flight_search` / `booking_flow` / `multi_tool` 的 0%**，
它们才反映真实的工具调用能力。

### 4.4 按可见性

| 可见性 | n | accuracy | pass^4 |
|---|---|---|---|
| seen | 67 | 38.8% | 32.8% |
| unseen | 39 | 39.1% | 35.9% |

两者**几乎相同**。需要注意：`seen`/`unseen` 标签由骨架哈希派生，**不读取训练数据**，
因此这个差值**不能读作泛化差距**。`scripts/prepare/verify_all.py` 每次运行都会打印该警告。

## 5. 「格式对但值错」这一退化模式

### 5.1 为什么要单独监控

格式正确率上升**本身不是好事**——它是必要不充分条件。如果模型学会"输出合法 JSON
但实体乱填"，任务成功率不会动，而格式率会虚高。

因此报告同时给出两个量，并要求它们**同向变化**：

| 指标 | 基线 |
|---|---|
| 格式错误条数 | 141 / 424（33.3%） |
| 「格式对但值错」占比 | 见 `error_analysis.json` 的 `format_ok_value_wrong_rate` |

### 5.2 与后续实验的对照

在真实消融中这一监控发挥了作用：

| 实验 | 格式错误条数 | 成功条数 |
|---|---|---|
| 仅 SFT | 0 | 342 |
| 格式约束 DPO | 1 | 346 |
| 错误恢复 DPO | 10 | 310 |
| 联合方案 | **74** | 268 |

联合方案的格式错误从 0 涨到 74，同时成功率下降——**格式退化与能力退化同时发生**，
这正是该监控想捕捉的信号。

---

## 6. 根因分析

### 6.1 格式遵从是首要瓶颈

141 条格式错误里，**53 条属于"只承诺要查"或"完全不输出标签"**。这说明模型
理解任务意图（它知道要查航班），但**没有把意图落成结构化调用**。

对 1.5B 模型而言，格式指令的遵循能力随参数量下降最快，这与"小模型工具调用能力弱"
的普遍观察一致。

### 6.2 参数错误集中在需要外部知识的字段

111 条参数错误中，多数涉及机场三字码与日期换算。这两类字段的共同点是
**不能从用户话里直接抄**：

- 机场三字码：用户说「北京」，期望 `PEK`（需世界知识）
- 日期：用户说「本周五」，期望绝对日期（需换算）

`weather_advisory` 的 90% 准确率恰好从反面印证：那里的 `city` 参数**可以从用户话里
直接抄**（用户说「绵阳」，期望也是「绵阳」），所以不出错。

### 6.3 三个 0% 类别的共同点

`flight_search` / `booking_flow` / `multi_tool` 都需要**多次生成或依赖上下文推理**：

- `flight_search`：需要生成 3 个参数且全部正确
- `booking_flow`：需要从工具观测里读出 `flight_id`
- `multi_tool`：需要结合前一轮的工具结果

未训练模型在这些任务上的失败是**确定性的**（pass@4 仅比 accuracy 高 4.5pp），
说明它不具备这些能力，而非"偶尔出错"。

## 7. 诊断结论 → 改进方向

### 7.1 错误类别到方案设计的映射

| 错误类别 | 占失败 | 对应的偏好对设计 |
|---|---|---|
| FORMAT_ERROR | 54.4% | `format_constraint`：合法 `<tool_call>` ↔ 纯文本承诺 / 坏 JSON |
| PARAM_ERROR | 42.9% | `param_constraint`：真实实体 ↔ 占位符 / 错一个字符的值 |
| HALLUCINATION | 0.0% | `tool_selection`：白名单工具 ↔ 命名变体假工具 |
| WRONG_TOOL | 2.7% | `tool_selection`：正确工具 ↔ 语义相邻的真实工具 |

映射不是拍脑袋配对：每一类偏好对的 `chosen`/`rejected` 对比点直接对应一类错误的
**具体表现形式**（见 `src/eval/error_taxonomy.py` 的 `CATEGORY_REMEDIES_ZH`）。

### 7.2 基线给出的三个判断

1. **改进空间主要在格式与参数**，这两类占 97.3% 的失败。
2. **幻觉不是基线的瓶颈**（0 条），因此工具选择类偏好对在基线阶段的边际收益有限。
3. **三个 0% 类别是能力缺失**（确定性失败），单靠提示词或解码参数无法解决，
   必须在训练数据里提供对应能力的示范。

### 7.3 后续验证

上述判断在 `docs/ablation/results.md` 中得到验证：

- SFT 把三个 0% 类别全部提升到 93% 以上，格式正确率达到 100%
- 整体准确率 38.9% → 80.7%
- 格式约束 DPO 在 424 次采样中仅 1 次格式错误，且在 8 个类别上零回退

## 8. 诊断产物的获取方式

```bash
# 基线评测（GPU，约 12 分钟）
python scripts/eval/run_baseline.py --label baseline  --num-samples 4

# 错误分析 + 出图（CPU）
python scripts/eval/analyze_errors.py --label baseline 
```

产物：

```
experiments/baseline/
├── eval_report.json        分行指标、分组下钻、逐任务结果
├── predictions.jsonl       424 条逐次采样原始输出
├── error_analysis.json     错误分布、交叉表、子类型统计
├── limitations.md          自动生成的已知限制
└── failure_cases/          失败案例（供人工检查）
```
